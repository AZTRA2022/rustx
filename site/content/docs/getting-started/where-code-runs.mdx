---
title: "Where your code runs"
description: "Which process runs what, and why there is no server, no client and no hydration."
---

Next.js splits an application into server code and client code, and a good
part of learning it is knowing which side a line is on. rustx has no such split.
There is no server, no `use client`, no server rendering and no hydration.
Everything you write runs on the machine of the person using the window, in
one place. This page says where.

## One executable, one window

The executable the user started holds your Rust code and the window. The window
is drawn by the webview the system already has: WebView2 on Windows, WKWebView
on macOS, WebKitGTK on Linux. The page that webview shows holds a small
interpreter and the JavaScript libraries you installed, and nothing of yours
that is written in Rust.

| | |
|---|---|
| your **process** | runs your Rust code, owns the state and the window handle |
| the **webview** | draws the DOM and runs the page's JavaScript |

`App::new` opens the window and runs until it closes. A second window is the
same executable started again, with its own state: see
[several windows](/docs/the-window/several-windows).

## Your pages run in your process

The pages of `app/` are compiled into the executable as ordinary Rust. They run
on the thread that owns the window. That is the choice the rest follows from:

- the state, the cells of the components, the router and the handlers all live
  in this one process, and an `onClick` is a function call in it. The page
  tells your process that something was clicked; it does not run your handler;
- a component returns an `Element` tree. The framework compares it with the
  previous one and sends the difference to the page as a list of commands,
  once per frame. Nothing is rendered on a server and nothing is rebuilt from
  HTML;
- a keystroke in a field reaches your handler after a short trip to the page
  and back. The framework numbers each input, so a value it sends back that is
  older than what the user has typed is ignored and never overwrites it.

## Threads

| | |
|---|---|
| the **window thread** | draws, runs handlers, owns all state. State is neither `Send` nor `Sync` |
| a thread from `task(…)` | yours. It never writes state: it posts a job, and the next frame applies it |
| the `rustx-async` workers | the tokio runtime behind `task(async { … })`. Started on the first call, never before |

A component is asked for the screen as it is now, so it cannot wait. A loop
that does not end freezes the window, and after five seconds the engine prints
which component has been drawing since. Work that waits goes in a task. See
[keep, effect, task](/docs/getting-started/keep-effect-task) and [async](/docs/async).

## Where the JavaScript libraries are

React, shadcn and the other libraries run in the page. A component of a library
is a node that React draws inside the tree rustx draws. What passes between the
two is JSON: `null`, a boolean, a number, a string, a list or an object of these.
A function crosses only as a callback: the library calls it, and your Rust closure
runs in your process a moment later. Its return value does not come back to the
library.

Code in your own `.rsx` pages is never compiled to JavaScript. See
[JavaScript libraries](/docs/javascript-libraries) and
[props that cross](/docs/javascript-libraries/props-that-cross).

## What crosses between the page and your process

- the events of the DOM: a click, an input, a key, reduced to a short record;
- the commands of each frame, from your process to the page;
- a call to a native function you registered, which the page makes with a
  synchronous request and which answers with a value or an error;
- what only the window knows, such as the real path of a dropped file, and what
  only the window can do, such as obeying a window command.

A native registered with `register_native` runs on the window thread while the
page waits for it, so a slow one freezes the page. Short answers are what it is
for. For work that takes time, register it with `register_async_native`: the
page gets a promise, the future runs on the async runtime, and the window keeps
drawing and answering clicks until the promise settles, as with a Server Action
awaited from a component.

Two windows are two processes, so two separate states. The `let mut` at the
top of a page is not shared between them.

## The system modules

The clipboard, the dialogs, the tray and the shortcuts are ordinary function
calls made from your page code. A dialog runs its own message loop while it is
open, so the window stays drawn and the call still reads like a function. See
[the system](/docs/the-system).

## If you come from Next.js

| | |
|---|---|
| Server Components | no equivalent. Nothing runs before the window |
| `use client` | every component already runs on the client |
| a Route Handler or Server Action | a Rust function called directly from the page, or a native registered for JavaScript. See [the Rust bridge](/docs/javascript-libraries/rust-bridge) |
| hydration | none. The framework builds the DOM from the tree |
| fetching in a component | a task, which writes state when the response arrives. See [network calls](/docs/async/network-calls) |
