title: "The file manager"
description: "Show a file in its folder, put it in the recent documents, and own a file extension."
---

Three things a document application owes its system: "Show in folder"
after an export, a place in the system's recent documents, and a
double-click on a `.myformat` file that opens the right program.

```rust
use rustx::os::shell;

shell::reveal(&exported)?;            // open the folder, file selected
shell::remember_recent(&saved)?;      // add it to the recent documents
shell::open_url("https://rustx.dev")?; // hand a link to the user's browser
shell::register_scheme(&scheme)?;     // answer myapp://…
```

`shell` is reached through `rustx::os` — see
[the system](/docs/the-system). It is not the same thing as
[`terminal`](/docs/the-system/the-terminal), which runs a script; this
one talks to the desktop's file manager.

## Reveal

```rust
let mut said = String::new();

fn Exported(path: std::path::PathBuf) -> Element {
    return <div>
        <button onClick={move |_| {
            if let Err(why) = rustx::os::shell::reveal(&path) {
                said = why.to_string();
            }
        }}>Show in folder</button>
        {if said.is_empty() { <></> } else { <p>{said.clone()}</p> }}
    </div>;
}
```

It opens the folder **with the file selected**, which is what "show in
folder" means and what opening the folder alone does not do. A file that
does not exist is refused by name rather than opening an empty window.

## Recent documents

```rust
shell::remember_recent(&saved)?;
```

Adds the file to the system's own recent list — the one the Start menu's
jump list, the Dock and the desktop's "Recent" entry read. An
application that opens documents should call this every time it saves or
opens one; it costs nothing, and its absence is the kind of thing users
notice without being able to name.

There is no call to *read* the recent list back, and no call to clear
it. The list belongs to the user.

## Owning an extension

```rust
use rustx::os::shell::{self, Association};

let mine = Association {
    extension: "rxdoc".to_string(),               // no dot
    id: "MyEditor.Document".to_string(),          // stable, yours
    description: "MyEditor document".to_string(), // what the explorer shows
    program: std::env::current_exe()?,            // gets the path as argv[1]
};

shell::associate(&mine)?;
// and to undo it
shell::dissociate(&mine)?;
```

| | |
|---|---|
| `extension` | without the dot. `".rxdoc"` is refused, and says to write it without |
| `id` | an identifier of your own, letters digits and dots. A space is refused |
| `description` | the type name the file manager displays |
| `program` | the executable the path is handed to as its first argument |

`Association::checked()` runs those rules, and `associate` runs it for
you before touching anything.

### For this user, and without administrator rights

On Windows this writes under `HKCU\Software\Classes` — the user's own
hive. An application that demands elevation to tick a box is an
application that gets uninstalled.

The consequence to know in advance is the same one as
[autostart](/docs/the-system/start-with-the-session)'s: the registered
path is the executable's path **now**. During development that is the
binary in `target/debug/`, and a `cargo clean` leaves an association
pointing nowhere. An application that moves rewrites its association.

### And the other half, which is not written

Registering the extension is only one side of a file association. The
other side is receiving the path when the user double-clicks: that
arrives as `argv[1]` in a **new** process, so an application that is
already open needs [a single instance](/docs/the-system/a-single-instance)
to hand the path over to the window that exists.

```rust
// in main, before the window
let Ok(_only) = instance::Only::one("com.example.my-editor") else {
    instance::hand_over("com.example.my-editor", &std::env::args().skip(1).collect::<Vec<_>>())?;
    return Ok(());
};
```

That combination works, and it is the same combination a URL scheme
needs.

## A link in the user's browser

```rust
rustx::shell::open_url("https://rustx.dev/docs")?;
rustx::shell::open_url("mailto:support@example.test?subject=Crash")?;
```

The address goes to the system, which gives it to the browser the user
chose. The page is drawn by Chrome or Safari or Firefox, in their
process, with their sandbox, and the application is not involved — which
is why this is not in conflict with the rule that
[a rustx window loads only local content](/docs/the-system/security).
Nothing remote ever enters this process.

Three schemes and no others: `https`, `http` and `mailto`. The refusal
of the rest is the security answer rather than its absence. `file://`
would turn "open this link" into "read a local file", and a scheme of
somebody else's choosing is an arbitrary program started with an
argument from a page. An application that wants to open a file has
`reveal`; one that wants to start a program has
[`terminal`](/docs/the-system/the-terminal).

## Owning a URL scheme

```rust
use rustx::shell::Scheme;

let scheme = Scheme {
    scheme: "myapp".to_string(),              // no colon, no slashes
    name: "My App".to_string(),               // what the system shows the user
    program: std::env::current_exe()?,
};
rustx::shell::register_scheme(&scheme)?;
```

This is Electron's `setAsDefaultProtocolClient` and Tauri's deep link.
After it, `myapp://invoice/42` in a browser, an e-mail or another
application starts this one with the whole address as its first
argument — and with [a single instance](/docs/the-system/a-single-instance)
held, a second start hands the address to the copy that is already
running instead, which is what makes a link open the window that is
already there rather than a new one.

Per user, never for the machine: a system-wide handler needs
administrator rights, and a desktop application that asks for them to
register a link is one people stop installing.

Ten schemes are refused by name — `http`, `https`, `file`, `mailto`,
`ftp`, `data`, `javascript`, `about`, `tel`, `sms` — because taking one
would break the browser, the mail client or the file manager for the
whole user account. So is anything that is not a scheme by RFC 3986's
rules: a letter, then letters, digits, `+`, `-` and `.`.

`unregister_scheme` undoes it, and a scheme that was never registered
is not an error.

## Platforms

| | |
|---|---|
| **Windows** | written and run. Explorer for `reveal`, `shell32`'s recent documents, `HKCU\Software\Classes` for associations and schemes, `ShellExecuteW` for a link |
| **Linux** | written, never run. The file manager is reached over D-Bus, the recent list is `recently-used.xbel` (and is refused), and a scheme is a `.desktop` file with `x-scheme-handler/` plus `xdg-mime default`. A link is `xdg-open` |
| **macOS** | written, never compiled for a Mac. `open` for both a link and `reveal`; a scheme is `CFBundleURLTypes` patched into the running bundle's `Info.plist`, then `lsregister -f` |

A file **association** on macOS is still refused, and for a reason that
does not apply to a scheme: an association is declared by the bundle
(`CFBundleDocumentTypes`) and `LSSetDefaultRoleHandlerForContentType`
can only make an application the default for a type its bundle already
declares.

`crates/rustx-os/tests/shell.rs` writes a real association, reads it
back out of the registry with `reg query`, and undoes it. `reveal` is
only tested in its refusal of a missing file: calling it for real would
open Explorer in front of whoever is running the suite. See
[platforms](/docs/the-system/platforms).
