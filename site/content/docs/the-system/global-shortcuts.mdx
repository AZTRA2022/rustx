```rust
use rustx::shortcut;

let capture = shortcut::Shortcut::listen("Ctrl+Shift+R")?;

if capture.pressed() > 0 {
    start();
}
```

They work when the window does **not** have focus: that is the whole point.
A web page cannot hear a keyboard that is not meant for it.

## What is read

`pressed()` returns **how many times** the combination was pressed since the
last read, and resets the counter to zero. There is no callback to
install: something has to ask.

The place that asks is a `task`, which owns the `Shortcut` and posts what
it saw into state. It cannot be the body of the component: a component
may not write state while it is being drawn, and the compiler says so.

```rust
let mut shots = 0;

fn Capture() -> Element {
    task(move |alive| {
        let Ok(hotkey) = shortcut::Shortcut::listen("Ctrl+Shift+R") else {
            return;      // taken by another application; see below
        };
        while alive.get() {
            std::thread::sleep(std::time::Duration::from_millis(50));
            let times = hotkey.pressed();
            if times > 0 && alive.post(move || shots += times as usize).is_err() {
                break;   // the window is gone, or this component
            }
        }
    });

    return <p>{shots} captures</p>;
}
```

The thread ends with the component, the `Shortcut` is dropped with it,
and the combination goes back to the system. Nothing is cleaned up by
hand.

<Callout title="Or on the frame, without a thread">
`on_frame` runs a closure once per frame on the thread that draws, which
is also a place a write is allowed. Registered from an `effect((), …)`
so that it happens once per instance, it gives the same result with no
thread and no sleep to choose:

```rust
let mut shots = 0;

fn Capture() -> Element {
    let hotkey = keep(shortcut::Shortcut::listen("Ctrl+Shift+R"));

    effect((), move || {
        rustx::on_frame(move || {
            let times = hotkey.with(|found| {
                found.as_ref().map(|each| each.pressed()).unwrap_or(0)
            });
            if times > 0 {
                shots += times as usize;
            }
        });
    });

    return <p>{shots} captures</p>;
}
```

The difference that matters: a frame callback cannot be removed, so this
form belongs in a component that lives as long as the window — the root
`layout.rsx`. A `task` is the form for a screen that comes and goes.
</Callout>

`hotkey.keys()` returns the combination as it was written, to display it
in a settings screen. `keep` hands back a `Kept<Shortcut>`, which is
read with `with` — see [keep, effect, task](/docs/getting-started/keep-effect-task).

## What can be written

The modifiers: `Ctrl`, `Alt`, `Shift`, `Win`, in any order, separated by `+`.

The keys: letters and digits, `F1`–`F24`, `Space`, `Tab`,
`Enter`, `Esc`, `Backspace`, `Delete`, `Insert`, `Home`, `End`,
`PageUp`, `PageDown`, and the arrow keys `Left`, `Right`, `Up`, `Down`.

```rust
shortcut::Shortcut::listen("Alt+Space")?;
shortcut::Shortcut::listen("Ctrl+Alt+Shift+F9")?;
shortcut::Shortcut::listen("Win+Up")?;
```

What is not recognized is refused **by naming what was written**: the
error quotes the piece it could not read, quotes the whole combination it
was in, and lists the key names it does accept. `Ctrl+` with no key, and
a combination that names two keys, are each refused with their own
sentence.

The refusal arrives as `OsError::Platform`, so it reads
`the system refused: …` followed by that sentence. Those sentences are
still written in French and are being translated; the variant is what to
match on.

## A combination already taken

The system gives it out only once. If another application holds
`Ctrl+Shift+R`, `listen` refuses, and this is a case to draw rather than ignore:

```rust
fn Settings() -> Element {
    let hotkey = keep(shortcut::Shortcut::listen("Ctrl+Shift+R"));

    return hotkey.with(|found| match found {
        Ok(found) => <p>{found.keys().to_string()} is listening</p>,
        Err(why) => <p className="text-destructive">
            {why.to_string()} — choose another one
        </p>,
    });
}
```

This is also what happens to a `rustx dev` restarted too quickly: the previous
process held the combination, and it gives it back as it dies.

## The token releases it

A `Shortcut` released gives the combination back to the system. A
`Ctrl+Shift+R` that no application handles is a defect that the user can only
fix by restarting their session, and that is why this is an object with a lifetime and not a `register`.

In a settings screen where the user chooses their combination, it is `effect` that redoes the listening, and the earlier `keep` that is released:

```rust
let mut keys = "Ctrl+Shift+R".to_string();
let mut held = None::<shortcut::Shortcut>;

fn Settings() -> Element {
    effect(keys.clone(), move || {
        // Bound first: a page value is read by value, so `&keys` would
        // be a reference to the cell and not to the string in it.
        let wanted = keys.clone();
        held = shortcut::Shortcut::listen(&wanted).ok();   // the old one is released here
    });

    return <input value={keys.clone()} onInput={move |event| keys = event.value} />;
}
```
