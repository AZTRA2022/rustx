---
title: "Secrets"
description: "A token or a password kept where the system keeps its own, encrypted with the user's session."
---

An API token or a password has no business sitting in a plain-text
configuration file. Every desktop system has a store for them, encrypted
with the user's own session, and it is the **user** — not the
application — who can look inside it and take things out.

```rust
use rustx::os::secret;

secret::store("my-app", "someone@example.org", &token)?;

if let Some(token) = secret::fetch("my-app", "someone@example.org")? {
    sign_in_with(&token);
}

secret::forget("my-app", "someone@example.org")?;
```

`secret` is reached through `rustx::os` — see
[the system](/docs/the-system).

## Two names

A secret is addressed by a **service** and an **account**. The service is
the application, or the server the secret opens; the account is who it
belongs to.

| | |
|---|---|
| `store(service, account, secret)` | writes it, replacing whatever had those two names |
| `fetch(service, account)` | `Ok(None)` when there is nothing under them — not an error |
| `forget(service, account)` | removing what is not there is not an error either |

An empty service or an empty account is refused before anything is
written: a secret with no name cannot be found again.

## Where it actually goes

| | |
|---|---|
| **Windows** | Credential Manager, as a generic credential. The target reads `service/account`, and that is the name the user sees under "Windows Credentials" |
| **macOS** | the Keychain |
| **Linux** | the Secret Service — GNOME Keyring, KWallet |

The secret is stored as UTF-8, and comes back as it went in. On Windows
that is pinned by a test that stores a string with an accent and an
em dash and reads it back.

## What this does not do

- **It is not a vault for application secrets.** A key that belongs to
  *you* and must stay secret does not belong on the user's machine at
  all — not in the binary, not in the credential store. It belongs on a
  server you control, and the application calls that server. See
  [environment](/docs/tooling/environment).
- **It is not encryption.** What it gives you is the system's store,
  with the system's protection: readable by programs running as that
  user. It keeps a token out of a file that gets copied into a backup or
  pasted into an issue. It does not defend against code already running
  as the user.
- **There is no sign-in helper.** No OAuth flow, no loopback listener,
  no browser hand-off. rustx has no function that opens the system
  browser at all, by design — see [security](/docs/the-system/security).
  An application that signs in does the flow itself and puts the result
  here.

## A token read once

```rust
let mut token = String::new();
let mut problem = String::new();

fn Page() -> Element {
    effect((), move || {
        match rustx::os::secret::fetch("my-app", "me") {
            Ok(Some(found)) => token = found,
            Ok(None) => {}
            Err(why) => problem = why.to_string(),
        }
    });

    return <div>
        {if token.is_empty() { SignIn() } else { Signed() }}
        {if problem.is_empty() { <></> } else { <p className="text-destructive">{problem.clone()}</p> }}
    </div>;
}
```

The read is in an `effect((), …)` and not in the body of the component
because a component may not write state while it is being drawn. The
store is on disk and the read talks to the system, so it is not
something to do on every frame either.

## Platforms

| | |
|---|---|
| **Windows** | written and run. `crates/rustx-os/tests/secret.rs` stores a secret for real, reads it back, replaces it, removes it, and removes it twice |
| **Linux** | written; compiled and tested on a CI Linux runner, not driven on a desktop |
| **macOS** | written; compiled and tested on a CI Mac, not driven on a desktop |
