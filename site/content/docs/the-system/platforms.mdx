`rustx-os` is one folder per operating system, and a capability is **one
file per system** with the same function names in each. The module above
them never asks which machine it is on.

```text
crates/rustx-os/src/
  clipboard.rs          the API a page sees: the types, the words, no platform
  windows/clipboard.rs  Windows
  linux/clipboard.rs    Linux
  macos/clipboard.rs    macOS
  other/mod.rs          everything else, which refuses
```

## Written is not run

This is the distinction the rest of this page is built on, and it is the
one that matters when you are deciding whether to ship on a platform.

| | |
|---|---|
| **written** | the file exists and calls the platform's real API |
| **compiled** | it type-checks for that target |
| **run** | somebody executed it on that operating system and watched what happened |

The tests compile `linux/`, `macos/` and `other/` on whatever machine
they run on, through three `mod *_also_compiles` declarations in
`lib.rs`. That is worth having — a rename in the API above breaks here
rather than on somebody else's machine three weeks later — and it is
**much** weaker than it sounds: it type-checks those files against
*this* machine's target, so it catches a changed signature and a syntax
error, and nothing else.

<Callout type="warn" title="What the CI runs, and what only a person can">
Every pull request builds `rustx-os` on a GitHub Windows, macOS and Linux runner
and runs its tests there (`.github/workflows/ci.yml`): the macOS files compile
against the real Apple frameworks and the Linux ones against the real
libraries, and the tests that need no desktop pass. What a runner cannot do is
drive a desktop: no screen, no tray, no dialog answered by a person, no
camera. Those parts are written and type-checked, and have been seen to work
only on Windows. Each file says so at its own head.
</Callout>

## Capability by capability

**Windows** is written and run for every row. The other two columns say
what the file does, not that anyone has seen it do it.

| | Linux | macOS |
|---|---|---|
| `clipboard` | written — `wl-copy`/`xclip` | written — `pbcopy`/`pbpaste` |
| `notify` | written — `notify-send` | written — `osascript` |
| `autostart` | written — a `.desktop` file in `~/.config/autostart` | written — a `LaunchAgent` plist |
| `instance` | written — a Unix domain socket | written — the same socket code |
| `dialog` | written — `zenity`/`kdialog` | written — `osascript`'s `choose file` |
| `devices` | written — `/sys/class/video4linux` | written — `system_profiler` |
| `window` | written — X11 through `x11rb`, and Wayland through XWayland | written — `NSWindow`, compiled on a CI Mac |
| `shortcut` | **refuses.** Needs a desktop portal over D-Bus | written — Carbon's `RegisterEventHotKey`, compiled on a CI Mac |
| `tray` | **refuses.** Needs a `StatusNotifierItem` over D-Bus | written — `NSStatusItem`, compiled on a CI Mac |
| `about` | **refuses.** Linux has no system About panel: `GtkAboutDialog` is GTK's, and no desktop protocol defines one | written — the standard panel |
| `menu` | **refuses.** X11 and Wayland have no menu; a toolkit draws one, and linking GTK for it would cost the whole of GTK and a second event loop. Draw it in the page | written — `NSMenu`, compiled on a CI Mac |
| `data` | written — the XDG base directories | written — `~/Library/{Application Support,Caches,Logs}` |
| `update` | written. The HTTP under it is `curl`, then `wget` | the same |
| `attention`, `audio`, `bluetooth`, `capture`, `color`, `net`, `print`, `screen`, `secret`, `shell`, `system`, `terminal` | written | written |

`shell` grew two of its own since that row was written:
`register_scheme` is a `.desktop` file with `x-scheme-handler/` on Linux
and `CFBundleURLTypes` plus `lsregister` on macOS, and `open_url` is
`xdg-open` and `open`. A file **association** on macOS is still refused,
because an association is declared by the bundle rather than at run
time.

HTTP is the one capability with a different shape per platform rather
than a different implementation: Windows has WinHTTP, which every
Windows machine ships as a library, and macOS and Linux have no
equivalent that can be called without linking something — so there it
runs `curl`, then `wget`, and reads the answer on a pipe. That buys the
system's certificate store, the system's proxy settings and the system's
own security updates, and costs one process per request. A machine with
neither is told to install either.

The rows that say **refuses** are not oversights. A `.desktop` file
or a call to `notify-send` is a file or a command, which is why the rows
above them were cheap; a global shortcut and a tray icon each need a
live D-Bus attachment that the process has to hold open, which is a
larger piece of work than one file. They refuse by name rather than
doing nothing.

## What a refusal says

`OsError::Unsupported` names the capability and the platform:

```text
the clipboard is not available on this platform (linux)
```

A capability that is written but fails for a platform reason — a missing
`zenity`, a D-Bus that is not there — comes back as
`OsError::Platform`, which passes the platform's own words through.

<Callout type="warn" title="Two things the refusal does not do">
It does **not** name the file that would have to be written, which
earlier versions of this page claimed it did. And several of the
sentences inside `Platform(…)` are still written in French and are being
translated. Match on the variant rather than on the prose.
</Callout>

An application that wants to know **before** it draws a button asks
`supported()` — on the ten modules that have one:

```rust
if !tray::supported() {
    // do not draw the button rather than show an error
}
```

`about`, `autostart`, `clipboard`, `dialog`, `instance`, `notify`,
`shortcut`, `tray` and `window` have it, and it is the platform's own
answer: each `<os>/<capability>.rs` declares an `AVAILABLE` constant.
The twelve newest capabilities and `terminal` have **no** `supported()`;
they answer with a `Result`, and the refusal is the answer.

## The window

Everything [the window](/docs/the-window) commands — frameless, the
toggles, full screen, moving — is written for Windows and for Linux
(X11), and for macOS (compiled on a CI Mac). Windows is the only one
that has been seen to work. This is the part most tied to the system in
the whole framework: a window frame, a `WM_NCCALCSIZE` and Aero Snap
have no portable equivalent.

## One dependency per platform

| | |
|---|---|
| Windows | `windows`, Microsoft's own bindings, and only in this crate |
| Linux | `x11rb`, whose connection is pure Rust and links neither `libX11` nor `libxcb` |
| macOS | `objc2` alone, already in the tree through `wry` |

Nothing above `rustx-os` hears about any of them.

## What needs an eye

Some things cannot be checked by a test: whether an icon is really
there, whether a dialog opens in the right place. Those have an example
to run:

```sh
cargo run -p rustx-os --example choose_a_file
cargo run -p rustx-os --example tray_icon
cargo run -p rustx-os --example a_global_shortcut
cargo run -p rustx-os --example what_is_plugged_in
```

## Writing a platform

This is the most bounded job in the repository: one file, the same
function names as the facade, and an `AVAILABLE` constant where the
capability has one. Nothing about the engine or the compiler needs to be
understood to write one.

The most useful contribution today is not a new file but a **run**: take
the Linux or macOS half of a capability that is already written, run it
on that operating system, and report what happened. See
[contributing](/docs/tooling/contributing).
