This page is the one place that says what is missing and what is
broken. It is written while building real applications on top of the
framework, and it is kept current rather than kept tidy: an entry
leaves it when the thing works, not when somebody decides it has been
open too long.

The method behind every entry is the same: `rustx new` in a
neighbouring folder, the libraries installed by the commands given on
their own getting-started pages, no workaround, and no version chosen
to get a build through. The project points at the repository's sources,
so each fix is verified within seconds.

## The state of it

Ninety-six findings have been written down and closed since this page
began — the bug hunt against a project written from the outside, and
the log of gaps found while building on it. What is still open is
below, and the largest of it is not code.

## What is still open

- **An `async fn` written beside a page cannot reach a value of the page.** The compiler refuses this explicitly, and says where to declare the value. A page reads its values in an `async` block written *inside* the component, and an ordinary `async fn` takes what it needs as arguments. This is a limit, not a surprise.
- **A component `.await` that borrows a local** does not compile: the future leaves for the runtime, and a borrow from the thread that draws does not follow it. This is ordinary Rust, and the way out is to take the arguments by value — but the message comes from `rustc` and points at a column of a generated file that the developer has never opened. Documented, not refused.
- **A release built on a Mac or on Linux.** `rustx package` writes a Windows setup `.exe` that extracts itself (no Inno Setup), and that has been installed and uninstalled silently on Windows. The `.deb` is written by hand — the format is an `ar` archive of two tarballs, so no tool is needed — but it has only ever been read back by `dpkg-deb` in CI, never installed on a desktop. The macOS `.app` bundle, its `Info.plist`, the `.pkg` and the `.dmg` are written from Apple's own documentation and have never been built or opened on a Mac. Notarisation (`xcrun notarytool`), an `.rpm` and an AppImage are not written at all. See [packaging](/docs/tooling/packaging).
- **Completion and auto-import for an installed crate's own functions and components inside a `.rsx`.** `rustx-lsp` already relays `rust-analyzer` for the generated file; what a `.rsx` cannot yet do is list a crate's public items before the full path (`rustx::dialog::open`, `std::fs::read`) is typed out by hand, the way the Rust Analyzer extension does for ordinary `.rs` files. What exists today (`libraries.rs`, `suggest.rs`) covers the JavaScript libraries declared in `package.json`, not Rust crates.
- **Half-closed: a component name that collides with a library's.** `LineChart` written without its library's name can resolve to the wrong one if two installed libraries both export something by that name — `recharts` and `lucide-react` both do. The silent failure this used to cause is fixed (see below); the collision itself is not yet flagged at build time.
- **Half-closed: global shortcuts, the tray and window control on Linux and macOS.** The clipboard, notifications, autostart, a single instance, the camera list, and the file dialog are now real on both; these three still need a desktop portal over D-Bus (Linux) or `AppKit`/Carbon (macOS), which is a live attachment rather than a program to shell out to. See [What is not written](#what-is-not-written).
- **Open, and the largest of them: nothing outside Windows has ever been run.** Twenty-four capabilities are written for Linux and twenty-four for macOS, and the evidence that any of them works is that they type-check on a Windows machine. That is a syntax check, not a test. The most useful contribution to this project today is not a new file: it is running one that exists, on the operating system it was written for, and saying what happened. See [platforms](/docs/the-system/platforms).

## What is not written

These are not defects: they are things that no application has yet demanded hard enough to decide their shape.

- **Global shortcuts, the tray and window control, on Linux and macOS.** Everything else — the clipboard, notifications, autostart, a single instance, the camera list, and now the file dialog — is real on both, each by a program or a file the system already ships (`xclip`/`wl-copy`, `notify-send`, a `.desktop` file, `zenity`/`kdialog`, `pbcopy`/`pbpaste`, `osascript`, a `LaunchAgent` plist, a Unix socket, `/sys/class/video4linux`, `system_profiler`) rather than a library this crate would have to add. These three still need either a desktop portal over D-Bus (Linux) or `AppKit`/Carbon (macOS) — a live, in-process attachment rather than a command to run — and refuse by naming the platform and the feature. The Linux files are verified with `cargo check --target x86_64-unknown-linux-gnu`, which this machine can run without a Linux machine to run the result on; the macOS files have only been read over by hand, since no Apple target is installed here at all.
- **Dragging a whole title bar.** An event does not yet say **what** was pressed, so the handle of `window::drag()` sits on an empty space and not on the entire `<header>`, which would swallow the clicks on its own buttons.
- **Dragging a file *out of* the application** to the explorer.
  The other direction works and gives the real paths; this one requires an object that the window's process must hold for the whole gesture.
- **Closing to the system tray.** The icon does not keep the application alive: the message loop stops with the last window. The "minimize to the tray" behavior requires keeping a hidden window, and that is not written.
- **Video recording** beyond what the web view already gives — `MediaRecorder`, `getDisplayMedia`. A still image of the screen **is** written now: see [screens and capture](/docs/the-system/screens-and-capture).
- **A theme written by the framework.** `rustx new` could write the complete style sheet, which would make the framework the author of a theme. This is a choice to make, not an oversight; in the meantime, the minimal block is [documented](/docs/javascript-libraries/tailwind) where Tailwind is installed.
- **A sign-in helper.** No OAuth flow, no loopback listener, no state parameter, no code exchange. The two pieces such a flow needs now exist — [`shell::open_url`](/docs/the-system/the-file-manager) and [`shell::register_scheme`](/docs/the-system/the-file-manager) — and nothing wires them together. See [security](/docs/the-system/security).
- **A context menu on Linux.** [`menu::popup`](/docs/the-system/menus) is written for Windows and macOS; on Linux it refuses, because there is no menu in X11 or Wayland and a toolkit draws one. This one is unlikely to change: linking GTK to draw a grey rectangle would cost the whole of GTK and a second event loop. Draw it in the page.
- **A menu bar on Windows and Linux.** `menu::application()` installs the standard macOS one, and does nothing on the other two: a menu bar there belongs to a window, and the window is the web view's. Draw it in the page.
- **Placing a second window.** `What` takes a size and the system chooses the corner. [`os::screen`](/docs/the-system/screens-and-capture) says where the monitors are, which is half of what placing a window needs; the other half is not there.
- **A `.deb` installed on a real desktop, and anything at all on a Mac.** The formats are written and CI reads them back; nobody has double-clicked one.
- **A page cannot reach its own `Pane`.** `os::attention`'s `flash` and `progress` take one, and so does [`menu::popup`](/docs/the-system/menus), and `rustx::window` never hands the page one — so a page cannot put progress on its own taskbar icon or open a system menu. `badge` takes no window and is callable from anywhere. This is now the single gap that blocks the most other things.
- **A path parameter is not percent-decoded.** `/search/caf%C3%A9` reaches the page as `caf%C3%A9`. Only the query string is decoded, and `with_query` is the lossless way to carry text. See [parameters](/docs/the-router/parameters).
- **The refusal does not name the file to write.** `OsError::Unsupported` names the capability and the platform and stops there, and several `OsError::Platform` sentences are still written in French. Both are being worked on.

## What the logs have closed

For those who want to know what the two nights of bug hunting changed.

**The router** was measured against Next's, and what it lacked was written: the *query string*, the catch-all `[...path]`, the route groups `(section)`, `forward` and `replace`, the parameters of a `Layout`, `loading.rsx` and `error.rsx` per segment, and a readable history stack.

**The JavaScript boundary**: an `Element` can be a child of a library component, `Event` carries the value, the key, the target and the modifiers — including on a tag written inside a React subtree — `Value` has its accessors, and a callback receives all of its arguments.

**The compiler**: a dozen rewrites that emitted wrong Rust, each with the test that had found it. And the comments of the markup, which were shown on screen: the three forms — `//` at the start of a line, `/* … */`, and `{/* … */}` — are read and discarded, between the children as between the attributes; `see https://example.com` stays a sentence, and that is a law.

**The window**: `toggle_maximize()` and `toggle_fullscreen()`, because a title bar does not have two buttons but one that toggles; the place from before full screen retained and restored; and the **seven pixels** that Windows painted above a frameless window, taken back by `WM_NCCALCSIZE` without losing the resize edges.

**What a style sheet must carry.** This one was not in the framework, and it was worse: nothing complained. `--background` declared without `@theme inline` makes `bg-background` a word in an attribute, and the window opens white. This is said where Tailwind is chosen, and three laws measure it in the window: the background color, the text color, and the effective font.

**Linux and macOS got five capabilities each, by the same idea applied twice.** `rustx-os` already shelled out to `xclip`/`notify-send` for two of Linux's capabilities; this extended that to the clipboard, notifications, autostart, a single instance, the camera list and the file dialog on both platforms, each by a program or a file the system already ships rather than a library this crate would have to add — a `.desktop` file and a `LaunchAgent` plist for autostart, a Unix domain socket for a single instance (the one piece both platforms share verbatim, being both Unix underneath), `/sys/class/video4linux` and `system_profiler` for the camera list, `zenity`/`kdialog` and `osascript` for the file dialog. The Linux files are checked against the real `x86_64-unknown-linux-gnu` target; the macOS ones, with no Apple target available to check against at all, are read over by hand only.

**What a night of actually running the stress-test application found (written in the CEF era, kept as history).** A comment written on the line before a write to a page value cancelled that write — the code that decides whether what follows is a statement or an operator only looked back over whitespace, not over a `//` or a `/* … */` in the way. `style="width: 50%"` crossed the boundary to a library component as a string, and React refused it outright (error #62); it is translated into an object now. A component name that collided with an installed library's own (`LineChart` resolving to an icon library rather than to `recharts`) used to take the whole screen down without a word — React error #130 — and now says which component threw and why. `router::replace` called from an `async` block did nothing, because the router lived in thread-local storage and a future does not always run on the thread that opened the page; it is shared by the whole process now. `rustx dev` rebuilt the project forever, because every generated file got a new timestamp on every build even unchanged; every write the compiler makes now compares content first. A window left open in one project could make the other fail to build at all (`Access is denied`, `os error 5`) because both share a CEF binary that gets deleted and recopied on every build; `rustx build`, `rustx run` and `rustx dev` now catch this and name it before cargo runs — but a plain `cargo build`/`cargo run`, which never passes through that code, still shows the raw error, since there is no hook to catch a dependency's build-script failure from outside cargo itself. `rustx new` asked for `rustx = "0.1"`, which cargo's own rule for 0.x versions does not satisfy once the framework reaches 0.2 — new projects were silently getting the version from before. And two reported directly against the stress-test application: `rustx new` left nothing for the first `npm install` to write into, and a `rust-analyzer` that died mid-session left this language server mute for the rest of it; both write a file or restart a process that they previously left for the developer to notice and fix by hand.

**An application that ships (also from the CEF era: `libcef.dll` no longer exists).** Six of the rows that said "not written" in the [migration table](/docs/getting-started/migrating) have code behind them now, and they were one problem wearing six hats: a rustx application could be built and not released. `assets/` travelled by absolute path, so a copied folder opened a blank window; there was no data folder, no package, no installer, no signature and no updater. Now `#[rustx::main]` puts `assets/` inside the binary, [`rustx::data`](/docs/the-system/app-data) is the folder each system keeps for an application, [`rustx package`](/docs/tooling/packaging) produces the folder, the `.zip`, the manifest with a digest per file and the platform's own installer, `signtool` and `codesign` run when the environment names a certificate, and [`rustx::update`](/docs/tooling/packaging) installs the newest release from a GitHub release page — checking the size and the digest, and renaming the running executable out of the way, which is how a file in use is replaced on Windows. Three smaller rows went with them: a link in the user's browser, a URL scheme, and printing the window through Chromium's own preview.

**The editor stopped fighting the macro.** `#[rustx::main]` does real work as part of its expansion — it compiles the pages, and it ran the JavaScript bundler, which is `esbuild` in a child process. `rust-analyzer` re-expands a proc macro on every keystroke and gives it a few seconds, so the bundler ran per keystroke, timed out, and took the expansion with it: every item below the attribute reported as an error, and the completion stopped. A bundler failure was also a `compile_error!`, which showed an application whose `npm install` had not been run a red `#[rustx::main]` telling it to run `npm install`, in an editor, for a file nobody had touched. An expansion asked for by `rust-analyzer`'s own proc-macro server now skips both the bundler and the assets.

**And the server answers nine more questions.** `typeDefinition`, `implementation`, `references`, `documentHighlight`, `signatureHelp`, `documentSymbol`, `foldingRange` and `inlayHint`, all forwarded to `rust-analyzer` and reported at the page's own coordinates — which works because a generated page keeps its own line numbers. `rename`, code actions and formatting are refused on purpose: the first two answer with edits whose columns belong to the generated file, and the third would reformat a `.rsx` as Rust. See [the editor](/docs/tooling/the-editor).
